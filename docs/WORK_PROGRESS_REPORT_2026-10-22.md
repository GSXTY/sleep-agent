# 睡眠呼吸设备 AI Agent 工作进度汇报

日期：2026-10-22

当前阶段：技术验证与 App 评审 Demo

---

## 一、一句话总结

目前已经完成一个可运行、可评估的睡眠呼吸设备 AI Agent 技术 Demo。它能够理解用户问题、检索产品资料、读取真实设备数据、生成单晚和周期报告、分析趋势与评分变化，并具备医疗安全边界、混合检索、模型降级、成本控制和移动端演示能力。

当前版本定位为技术验证和 App 评审 Demo，不是正式生产版本。

按当前目标估算：

- 核心 Agent 与 Demo：约 80%
- 真实后台数据接入：约 65%
- 异常监测与内部预警：约 25%
- 正式产品化：约 40%～50%

## 二、这个 Agent 是什么

它不是简单地在 App 中接入一个大模型，而是一个受控的睡眠呼吸设备业务 Agent。

核心原则：

> 事实、报告和安全边界由程序确定；大模型只负责理解问题和组织语言。

这样可以同时利用大模型的理解能力和规则系统的确定性，避免模型编造设备参数、治疗数据或医疗结论。

当前支持：

- 普通闲聊和通用问答
- 产品原理、功能、操作、维护和故障排查
- AHI、P95、漏气量、潮气量、分钟通气量等指标解释
- 日期、星期和时间查询
- 单日、近 7 天和近 30 天设备数据查询
- 单晚报告、周报和月报
- 两次治疗数据对比
- 趋势、平均值、中位数、波动和异常日期分析
- 设备评分及三个分项变化分析
- App 报告结构化解读
- 调压、诊断、用药和停用等安全边界拦截
- 模糊问题追问和候选选项
- 来源折叠、用户反馈和 Bad Case 回流
- 手机 H5 Demo 和 WebView 接入准备
- 同一会话串行处理和模型并发上限
- SSE 状态推送及校验后的安全答案推送
- 一条消息包含多个产品问题时按子问题分别检索并逐项回答

## 三、系统架构

```text
手机 App / H5 / 命令行
          ↓
统一 API / 对话入口
          ↓
安全边界与时间语义层
          ↓
意图识别和查询规划
          ↓
┌─────────────────────────────────────┐
│ 设备数据源      知识检索层           │
│ sample/backend  BM25 + 向量 + RRF    │
│ 产品文档        指标知识库           │
└─────────────────────────────────────┘
          ↓
确定性数据事实层
报告、趋势、对比、评分拆解
          ↓
大模型语言组织
普通问答、产品问答、数据解读
          ↓
输出校验与降级
数字白名单、禁止语、医疗边界
          ↓
结构化响应、来源、日志和反馈
```

### 1. 入口层

支持三个入口：

- `chat.py`：Windows 命令行 Agent
- `demo_server.py`：手机 H5 Demo
- HTTP 探针接口：验证 App 和 WebView 接入

三个入口复用同一套 Agent 管线，避免命令行与 App 行为不一致。

### 2. 路由与编排层

处理顺序固定为：

1. 安全检查
2. 型号纠错和功能确认
3. 日期、报告范围及意图确认
4. 报告、趋势和对比分析
5. 查询规划
6. 产品文档或设备数据检索
7. 大模型回答
8. 输出校验与规则版回退

安全判断始终位于最前。即使问题前面增加“你好”等问候，也不能绕过安全边界。

### 3. 知识与数据层

- 产品资料统一转换成 Markdown
- 按章节、段落和内容类型切片
- 说明书、内部技术资料、FAQ 和示例资料分目录管理
- 设备数据支持 sample 与真实 YA70 后台接口
- 后台压力字段从 Pa 自动转换为 hPa
- 缺失字段不补 0，不推断不存在的治疗数据
- 多晚数据构建历史序列，支持趋势和阶段比较

### 4. 模型层

- 聊天模型：DeepSeek，OpenAI 兼容接口
- 向量模型：Ollama `bge-m3`
- 检索策略：BM25 + 向量检索 + RRF 融合
- 模型不可用时自动回退规则版
- 指标定义直接使用本地知识库，不依赖模型
- 报告和分析不调用大模型，保证稳定性

### 5. 校验与安全层

- 模型输出中的数字必须能在材料中找到
- 禁止编造日期、压力、AHI、漏气或设备参数
- 拦截调压、诊断、用药和停用等高风险请求
- 数据缺失时明确说明“未提供”
- 单晚数据不能外推为长期结论
- 内部模型错误不显示给用户
- 验收、降级和缓存信息写入日志，不进入用户正文

## 四、主要技术特点

| 技术点 | 当前实现 |
|---|---|
| 开发语言 | Python 3.10+ |
| 运行时依赖 | 核心功能仅使用 Python 标准库 |
| 聊天模型 | DeepSeek OpenAI 兼容接口 |
| 向量模型 | Ollama + bge-m3 |
| 产品 RAG | 规则检索 + BM25 + 向量检索 + RRF 融合 |
| 文档切片 | 按标题、章节、段落和表格结构化切片 |
| 数据源 | sample 与真实 YA70 日期区间接口 |
| App Demo | HTML/CSS/JavaScript，手机 WebView 可嵌入 |
| 报告 | 确定性规则生成，不依赖模型 |
| 数据分析 | 趋势、阶段对比、波动、离群日和评分分项拆解 |
| 安全 | 安全红线前置、数字白名单和禁止语校验 |
| 降级 | 模型、校验或向量失败时自动回退 |
| 成本 | 公共问答缓存、上下文预算、检索数量预算和 token 日志 |
| 测试 | 416 项单元测试、79 条端到端行为评测 |
| 并发与流式 | 会话锁、模型并发上限、SSE 状态和安全答案推送 |
| 部署 | Windows 一键 CMD、局域网手机访问 |
| Git | 私有 GitHub 仓库，敏感配置未上传 |

最重要的三个技术特点：

1. 事实计算和语言表达分离  
   AHI、漏气、压力、评分和趋势由程序计算，大模型不能自行生成这些数字。

2. 混合检索而不是只做向量匹配  
   产品型号、错误码和参数名需要关键词精确匹配；口语问题需要向量语义匹配。

3. 安全红线不交给大模型判断  
   调压、诊断、用药和停用必须在规则层直接拦截。

支持产品原理、工作模式、使用步骤、清洁维护、耗材、错误码和 App 操作等问题。

## 六、成本优化完成情况

已完成第一轮成本控制：

- 高频公共产品问答使用 1 小时内存缓存
- 产品问题默认不携带无关历史
- 设备数据最多带最近 3 轮
- 普通对话最多带最近 4 轮
- 产品检索从 6 个候选降为 4 个
- 产品回答限制 240 tokens
- 设备解读限制 280 tokens
- 通用对话限制 320 tokens
- 日志记录 `Tokens:输入/输出`
- 日志标记 `CACHE_HIT`

真实测试结果：

```text
第一次产品问题：约 6.9 秒，调用 DeepSeek
第二次相同问题：约 3 毫秒，缓存命中，不调用模型
```

## 八、当前缺点

### 1. 还不是生产系统

正式上线前仍需要：

- 正式服务端鉴权
- 根据登录 Token 获取用户 ID
- 租户和数据权限隔离
- 限流、幂等和审计
- 服务监控和告警
- 数据删除与隐私合规

### 2. 后台字段仍不完整

真实接口目前缺少：

- 逐条呼吸事件明细
- 事件发生时段
- 完整吸气、呼气时间比例
- 部分压力设定范围
- 部分呼吸概况字段

因此部分报告只能说明“未提供”或“无法判断”。

### 3. 图表还没有正式接入

当前以文字、指标卡和结构化数据为主。

压力趋势图、事件时长趋势图、呼吸频率趋势图和漏气趋势图仍需要 App 或后台图表接口配合。

### 4. 评测集规模还不够大

当前规则版评测 79 条、检索评测 27 条，足以做技术验证，但不足以覆盖真实用户的所有表达方式。

### 5. 大模型内容评测仍存在固定关键词误判

模型调用已经稳定，但部分回答虽然语义正确，没有完全命中评测脚本要求的关键词，还需要把评测升级为语义和事实双重检查。

### 6. 异常筛查还没有形成业务闭环

目前已有统计、趋势和波动分析能力，但还没有：

- 异常用户规则库
- 风险分级
- 内部预警队列
- 人工确认流程
- 告警闭环

## 九、主要困难点

1. 产品资料结构复杂  
   说明书包含大量表格、编号、注意事项和交叉引用，需要转换成适合检索的 Markdown，并避免错误章节被召回。

2. 设备数据不完整且格式不统一  
   字段名、单位、缺失值和日期语义都需要适配，不能为了报告完整而补 0 或猜测。

3. 医疗安全边界要求高  
   不能做诊断、不能建议用户自行调压、不能根据单晚数据判断长期疗效，回答必须明确边界。

4. 规则和模型之间需要平衡  
   全部用规则准确但不够灵活；全部交给模型灵活但容易编造，因此采用规则、检索、模型和校验组合。

5. 成本与体验需要平衡  
   模型回答自然，但调用有成本；规则版稳定，但语言不够灵活。当前通过缓存、上下文预算和确定性回答降低成本。

6. App 交互细节较多  
   手机端表格、输入框缩放、长回答滚动、来源展示和会话隔离都需要单独处理。
