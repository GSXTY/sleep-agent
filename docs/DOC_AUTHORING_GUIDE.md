# 产品资料维护规范

面向：写说明书、技术要求、FAQ、内部资料的同事。
目的：让 Agent 切得对、查得到、引用准，减少"答非所问"和"资料里明明有"。

**不需要为了 Agent 改写已有文档**。新增或修订时按下面的习惯写就行。

---

## 零、新增文档的标准流程（MD 优先）

检索目录里**只放 Markdown**，原始 DOCX 一律归档，不直接参与检索。

```powershell
# 1. 先预览：看标题数、表格数、前 1500 字
python tools/docx_to_md.py --src "D:\path\新文档.docx" --preview

# 2. 转换到对应目录（user 对客户 / internal 内部）
python tools/docx_to_md.py --src "D:\path\新文档.docx" `
    --out "product_docs/user/新文档.md" --title "新文档标题"

# 3. 原件归档（同名文件会被检索自动跳过）
Move-Item "D:\path\新文档.docx" "product_docs\_originals\"

# 4. 回归
python eval_retrieval.py --diagnose
python eval_agent.py
```

说明书这类大文档不要塞进一个 MD，用 `tools/build_product_md.py` 的拆分方式：
产品说明 / 使用指南 / 清洁维护 / 安全使用 / 技术参数 / 电磁兼容 / 售后 / 常见问题。

`product_docs/_originals/` 里的原件不参与检索；即使同名 DOCX 还留在 user/internal
（例如正被 Word 占用），加载器也会跳过它，避免和 MD 重复入库。

转换器会自动把 `图5-1`、`见4.2` 这类交叉引用改写成
`见《文档标题》图5-1（图注或"需对照原件查看"）`、`见《文档标题》4.2「章节名」`，
避免拆分后读者不知道编号指向哪里。

---

## 一、放在哪个目录

| 目录 | 内容 | 谁能看到 |
|---|---|---|
| `product_docs/user/` | 面向客户的说明书、规格、FAQ | 客户问答会引用 |
| `product_docs/internal/` | 内部技术要求、测试方法、注册资料 | 内部问答会引用，来源标"内部资料" |
| `product_docs/examples/` | 占位示例，非正式参数 | 仅演示，来源标"示例资料" |

支持 `.docx`、`.md`、`.txt`。一份文件一个主题，不要把说明书和技术要求混在一个文件里，
否则来源标注会含糊。

---

## 二、标题怎么写

切片的边界就是标题，所以标题决定"一节能不能被单独查到"。

| 规则 | 原因 |
|---|---|
| 标题 ≤ 40 字 | 超过 40 字会被当成正文，并进上一节 |
| 标题不以 `。；，：！` 结尾 | 以句末标点结尾的一律判为正文 |
| 编号统一：`1.3工作模式` / `6.4 更换空气滤芯` | 层级靠编号判断（1.3 是 1.3.1 的父级；`1.3.2` 能合并进 `1.3`） |
| 层级不超过 3 级（1.3.2） | 再深会让"父章节 + 子章节"的合并失效 |
| 不用「注意」「备注」「表格」当标题 | 这类无主题的章节会被当作噪声过滤掉 |

反例：`1. 手机安装配套 App 并完成注册。` —— 带编号、带句号，会被当成正文，
整条列表可能因此从检索里消失。

---

## 三、正文怎么写

1. **每个小节至少有一句正文**。标题下面直接跟图片、或者只有一句"如下所示："，
   这一节在检索里就是空壳。
2. **父章节开头列子项时，用冒号结尾**，例如
   「本系列设备具备以下几种工作模式：」——系统会把后面的子章节合并进父章节。
   如果写成「本节介绍工作模式。」，子章节就不会被带进来。
3. **单节控制在 400 字以内**（切片软上限 480 字）。太长的节会被拆开，
   后半段可能丢掉开头的前提。
4. **列表一行一项**，不要把多个要点塞进一句话或一张图。
5. **图片里的信息要有文字版**。docx 只能抽取文字，截图里的参数、界面说明读不到；
   只写「图5-6 系统设置界面」，Agent 就只知道有这张图。

---

## 四、表格怎么写

- 表格要有表头，且每一行是一条完整事实（`部件 | 周期 | 备注`）。
- 故障排除类表格建议一行一个症状，行首就是用户会说的词（`眼睛刺痛`、`面部变红`）。
- 不要把关键结论只放在合并单元格或图片里——抽取后可能变成孤立数字。

---

## 五、术语与型号

- 用用户会说的词。文档写「加温湿化器」、用户说「加湿器」时，
  需要把新说法补进 `synonyms.json` 或告诉开发加同义词，否则检索会漏。
- 型号统一写 `YA70`、`YA70A`、`YA70B20`；不要写 `Y70`、`YA-70` 这类变体。
- 错误码统一写 `E3`，不要写「错误三」。

---

## 六、数字与单位

- 每个数字带单位：`4.35 hPa`、`402 分钟`、`18.1 L/min`，不要只在表头写一次。
- 压力单位必须明确是 **Pa** 还是 **hPa**（接口给 Pa，展示用 hPa）。
- 没有测到的值写「未提供」或留空，**不要写 0**——0 会被当成真实测量值。
- 范围写成 `4 到 8 hPa`，不要写 `4~8` 这种容易被切碎的写法。

---

## 七、更新之后必须做的三件事

```powershell
python chat.py            # 输入 /docs 确认新文件被加载、切片数变化
python eval_retrieval.py  # 看 R@1 / R@3 有没有退步
python run_checks.py      # 单元测试 + 检索评估
```

再补一条：**用新文档里的 2~3 个真实问法各问一次**，确认能答到新章节。
新章节没被检索到，通常是标题太长、正文太少、或者术语和用户说法不一致。

---

## 八、真实踩过的坑

| 现象 | 原因 | 写法建议 |
|---|---|---|
| 问"产品模式有哪些"只答一句"具备以下几种" | `1.3工作模式` 正文只有引导语，四个模式在子章节 | 父章节导语以「：」结尾，或把要点直接写在父章节 |
| 「连接手机 App」整节消失 | 编号列表项被误判成标题，内容没进正文 | 列表项不要写成 `1. 长句子。` |
| 问"眼睛刺痛"答成胸部不适 | 整张故障表被切成一个大切片，单个症状被稀释 | 一行一个症状，行首就是症状名 |
| 问"湿度不够"查不到 | 文档写"加温湿化器"，用户说"湿度" | 补同义词或统一用词 |
| 截图里的参数答不出来 | docx 只抽文字，图片读不到 | 关键参数用文字再写一遍 |

---

## 九、提交前检查清单

- [ ] 标题 ≤ 40 字，没有句末标点
- [ ] 每个小节都有正文，不是只有图片或一句"如下"
- [ ] 父章节的引导句以「：」结尾（下面要列子项时）
- [ ] 单节 ≤ 400 字，或已拆成子章节
- [ ] 表格有表头，一行一条事实
- [ ] 数字带单位，缺失写"未提供"而不是 0
- [ ] 型号、错误码写法统一
- [ ] 放进正确目录（user / internal / examples）
- [ ] 跑过 `eval_retrieval.py` 和 `run_checks.py`
- [ ] 用 2~3 个真实问法验证过新章节能被答到
