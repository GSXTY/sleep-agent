# Bad Case 诊断与回流操作手册

适用范围：`<PROJECT_DIR>`
目标：遇到"应该答到却没答到"时，先判断问题在哪一层，再把它变成可重复回归的用例。

---

## 一、三步日常流程

```text
发现问题 → 诊断 → 记录 → 修复 → 回归
```

| 步骤 | 命令 | 产出 |
|---|---|---|
| 1. 诊断 | `python eval_retrieval.py --diagnose` | 每条用例在四层上的排名与归类 |
| 2. 记录 | `python record_badcase.py --query "..." ...` | 一条写入 `eval/cases.jsonl` 的用例 |
| 3. 回归 | `python run_checks.py` + `python eval_agent.py` | 新旧用例全绿才算修好 |

原则：**先定位，再动手**。同一个"答错"，可能是路由、闸门、召回、排序、校验五类问题，
修错层的代价是引入新问题。

---

## 二、诊断：问题在哪一层

```powershell
cd <PROJECT_DIR>
python eval_retrieval.py --diagnose
```

输出示例：

```text
问题                       闸门   放宽   向量   融合  结论
产品工作原理                    1    1    -    1  正常
YA70模式有哪些                 -   13    -    1  正常
湿化器怎么清洁                   2    2    2    2  排序（第 2 位）
```

### 四列的含义

| 列 | 含义 | 说明 |
|---|---|---|
| 闸门 | 正常覆盖率闸门下的关键词排名 | 主要看这一列判断"默认配置能不能召回" |
| 放宽 | `min_score=0, min_coverage=0` 时的排名 | 用来区分"闸门挡掉"和"根本没召回" |
| 向量 | 稠密检索（bge-m3）排名 | 不设排名下限，只看语义路 |
| 融合 | 最终混合检索排名（含标题命中前置） | 用户实际拿到的顺序 |

排名为 `-` 表示前 50 名里没有正确章节。

### 五种结论与对应处理

| 结论 | 典型特征 | 先改哪里 |
|---|---|---|
| **正常** | 融合第 1 | 不改检索；如果回答仍不对，看路由/校验 |
| **排序** | 融合第 2 名以后 | 标题命中、特征重排；先别动召回路 |
| **覆盖率闸门挡掉** | 放宽有、闸门没有 | 评估闸门阈值，或把该问题归入安全/固定话术 |
| **融合丢失** | 向量/放宽有、融合没有 | 调 RRF 权重，或加标题优先规则 |
| **召回失败** | 四条路都没有 | 补语料、修切片、加同义词；调权重无效 |

### 真实案例对照

| 案例 | 诊断结论 | 最后的修法 |
|---|---|---|
| 产品工作原理 | 关键词第 1、向量没进前 50、融合靠规则拉回 | 标题原文命中前置 |
| YA70模式有哪些 | 闸门挡掉（放宽第 13） | 检索前剥离型号 + 意图改写为"工作模式" |
| 产品模式有哪些 | 闸门挡掉 + 路由错误 | 产品模式意图识别 |
| 我有气胸可以使用吗 | 闸门挡掉 | 改为安全边界，不进检索 |
| 为什么眼睛有点痛 | 检索正常 | 修校验（分条编号被当数字） |
| 双水平是什么意思 | 检索正常 | 修校验（否定式提醒被误判） |

**结论：六个坑里只有两个跟排序有关。** 这就是为什么先诊断。

## 三、记录：把坑变成回归用例

### 记录一条

```powershell
python record_badcase.py `
  --query "YA70模式有哪些" `
  --mode 产品文档 `
  --section 1.3工作模式 `
  --contains AutoCPAP `
  --note "倒装问法，曾走到设备数据"
```

### 查看已登记

```powershell
python record_badcase.py --list
```

### 字段说明

| 字段 | 是否必填 | 用途 |
|---|---|---|
| `query` | 是 | 用户原话，必须和线上一致 |
| `expected_mode` | 三选一 | 期望模式前缀：产品文档 / 设备数据 / 安全边界 / 时间确认… |
| `expected_section` | 三选一 | 期望命中的章节名（子串匹配） |
| `expected_contains` | 三选一 | 回答里必须出现的关键内容，可多条 |
| `source` | 否 | 线上 / 测试 / 评审 |
| `note` | 否 | 踩坑说明，写给未来的自己 |

`expected_mode / expected_section / expected_contains` 至少要有一个，否则拒绝记录。
同一个问题只记一次。

### 两个评测怎么用它

| 评测 | 读取字段 | 作用 |
|---|---|---|
| `eval_retrieval.py` | `expected_section` | 检索回归：正确章节有没有排到前面 |
| `eval_agent.py` | `expected_mode` + `expected_contains` | 整机回归：模式、关键内容对不对 |

在 `eval_agent.py` 的报告里，这些用例会单列成「回流」类别，方便看"老坑有没有复发"。

## 四、回归：每次改完必须跑

```powershell
python run_checks.py        # 单元测试 + 检索评估
python eval_agent.py        # 整机行为评测
python eval_retrieval.py --diagnose   # 只在怀疑检索时跑
```

通过的判断标准：

1. 新增的 case 通过；
2. 原有 case 没有从通过变失败；
3. 用例数量与预期一致（数量变少说明有测试没被收集到）。

### 当前基线

| 项目 | 当前值 |
|---|---|
| 单元测试 | 304 项全部通过 |
| 检索用例 | 27 条，R@1 96% / R@3 100% / MRR 0.981 |
| 整机用例 | 47 条，全部通过（其中回流 7 条） |
| 排序问题 | 1 条（湿化器怎么清洁，融合第 2 位） |

## 五、判断要不要上重排器

先看三个数：

1. **R@3 是否已经接近 100%**：是，说明召回够用，问题只在排序；
2. **融合排在第 2~3 位的用例有多少条**：少于 3 条，先别上；
3. **评测集是否 ≥ 60 条**：不到 60 条，调参容易过拟合。

当前状态：27 条、排序问题 1 条。结论是**暂不上 Cross-Encoder**，
优先扩用例集。等"排序"类累积到 3~5 条，再做特征重排：

- 章节标题原文命中（已有）
- 问题词覆盖率（已有）
- BM25 归一化分
- 向量余弦

注意 BM25 是 0~30、余弦是 0~1，必须归一化后再加权，不能直接相加。

## 六、常见错误

| 错误做法 | 后果 |
|---|---|
| 看到一个 case 错就改权重 | 旧用例集体退步，且无法解释 |
| 把路由问题当排序问题 | 调了半天权重，问题还在 |
| 只修代码不记 case | 同样的坑三个月后再踩一次 |
| 用生产原话直接跑评测 | 含隐私信息；应脱敏后入库 |
| 用 20 条用例调到 100% | 过拟合，换一批问法就崩 |

## 七、下一步（按优先级）

1. 每周跑一次 `python eval_agent.py --llm`，把校验失败、答非所问的样本记进回流；
2. 把召回用例从 27 条扩到 60 条以上（真实用户问法优先）；
3. 当「排序」类达到 3~5 条时，做特征重排并跑网格搜索；
4. 只有在 MRR 卡住、排序类样本足够多时，才评估 Cross-Encoder。
